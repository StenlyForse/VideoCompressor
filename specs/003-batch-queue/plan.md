## 1. Технический контекст

Стек не меняется: .NET 10, Avalonia 12, CommunityToolkit.Mvvm, FFmpeg как внешний процесс. Новых зависимостей нет.

## 2. Ключевые решения

| Решение | Почему |
|---------|--------|
| **Логика очереди — в ядре** (`BatchCompressionService`), а не во ViewModel | Последовательная обработка, продолжение после ошибки, отмена и автоудаление «не меньше исходного» — это поведение, которое надо покрыть интеграционными тестами без UI (принцип 2 v1) |
| **Файлы анализируются (ffprobe) при добавлении**, а не при запуске | Пользователь сразу видит параметры и ошибки «не видео» (US-1.2); очередь при запуске не тратит время на анализ |
| **Путь результата вычисляется в момент начала файла** | Если пользователь, пока шла очередь, создал файл с тем же именем — коллизии не будет (правила v1, FR-001) |
| **Один файл = очередь из одного** | US-1.9: поле «Сохранить в» и вопрос «не стал меньше — удалить?» остаются только для единственного файла; при 2+ файлах результаты — рядом с исходниками, «не меньше» удаляется автоматически (US-4) |
| **Общий прогресс считается по длительности**, а не по числу файлов | Короткий и длинный файл весят по-разному; ETA по длительности честнее |

## 3. Ядро

### 3.1. `Compression/BatchCompressionService.cs`

```csharp
public sealed record BatchItem(string InputPath, VideoInfo Source, string? OutputPath = null); // OutputPath задан только для одиночного файла

public enum BatchItemState { Waiting, Compressing, Done, Failed, Cancelled, SkippedNotSmaller }

public sealed record BatchItemUpdate(int Index, BatchItemState State, CompressionProgress? Progress = null,
                                     CompressionResult? Result = null, string? Error = null, string? ErrorDetails = null);

public sealed record BatchProgress(int CurrentIndex, int Count, double Fraction, TimeSpan Elapsed, TimeSpan? Remaining);

Task<IReadOnlyList<BatchItemUpdate>> RunAsync(
    IReadOnlyList<BatchItem> items, CompressionSettings settings, bool deleteNotSmaller,
    IProgress<BatchItemUpdate>? itemProgress, IProgress<BatchProgress>? batchProgress, CancellationToken ct);
```

- Файлы обрабатываются по порядку через существующий `VideoCompressionService`.
- `FfmpegException`, `IOException`, `UnauthorizedAccessException` у файла → `Failed` с понятным текстом, очередь идёт дальше (US-2).
- Отмена → текущий `Cancelled` (недописанный файл удаляет `VideoCompressionService`), оставшиеся `Cancelled`, затем `OperationCanceledException` (US-3).
- `deleteNotSmaller` и результат ≥ исходника → файл удаляется, состояние `SkippedNotSmaller` (US-4). Для одиночного файла UI передаёт `false` и спрашивает сам, как в v1.
- `BatchProgress.Fraction` = (длительность готовых файлов + доля текущего × его длительность) / общая длительность; `Remaining` — по прошедшему времени, как в v1.

### 3.2. Изменения в существующем

Не требуются: `VideoCompressionService`, `MediaProbe`, `OutputPathResolver` используются как есть.

## 4. Приложение

### 4.1. `ViewModels/QueueItemViewModel.cs` (новый)

Состояние одного файла: путь, `VideoInfo` (или ошибка анализа), строка параметров, HDR-флаг, состояние, процент, текст состояния («Ожидает», «Сжатие… 47%», «Готово: 190,5 → 38,5 МБ (−80%)», «Ошибка: …», «Отменено», «Пропущен: сжатый файл не меньше исходного»), результат, команды «Убрать из списка» и «Показать файл».

### 4.2. `MainViewModel`

- `ObservableCollection<QueueItemViewModel> Items` вместо одиночных `InputPath` / `VideoInfo` / `LastResult`.
- `AddFilesAsync(IEnumerable<string>)` — из диалога (мультивыбор) и drag & drop: пропускает дубликаты (FR-002, сравнение путей по правилам ОС), анализирует каждый файл; не-видео добавляется с состоянием «Ошибка: файл повреждён или не является видео» и при сжатии пропускается.
- `ClearCommand`, `RemoveItem`.
- `OutputPath` / «Сохранить в» — только при `Items.Count == 1`.
- `CompressCommand` строит `BatchItem`-ы из готовых к сжатию файлов и вызывает `BatchCompressionService`; общий прогресс и итог («Сжато 4 из 5: 812,3 → 151,0 МБ (−81%), с ошибками: 1»).
- Повторный запуск после завершения сжимает только файлы в состоянии «Ожидает»; «Очистить готовые» убирает завершённые. *(Мелкое решение плана, не меняет спеку.)*
- Настройки, автовыбор формата, видеокарта, закрытие окна — без изменений.

## 5. Тестирование

| Уровень | Что | Как |
|---------|-----|-----|
| Интеграция (ядро) | 2 клипа + не-видео → 2 `Done`, 1 `Failed`, порядок обновлений | Сгенерированные клипы, CPU |
| Интеграция | Отмена на втором файле из трёх → 1-й `Done` и файл на месте, 2-й `Cancelled` без файла, 3-й `Cancelled` и не начат | Отмена по первому прогрессу 2-го файла |
| Интеграция | Уже сильно сжатый клип при `deleteNotSmaller` → `SkippedNotSmaller`, файла нет | Клип, заранее сжатый x265 с высоким CRF |
| Интеграция | Общий прогресс монотонный, заканчивается на 1 | Синхронный `IProgress` |
| Через UI (вручную скриптами UIA, как в v1) | SC-001…SC-003 на записях NVIDIA App пользователя | Контрольные точки в `tasks.md` |

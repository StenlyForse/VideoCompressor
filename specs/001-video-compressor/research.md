**Методика:**
- Звук в каждом прогоне кодировался в AAC 128 кбит/с.
- Качество оценивалось метрикой VMAF (модель по умолчанию v0.6.1) на каждом 3-м кадре.
- Кадры сопоставлялись по номеру: `setpts=N/(60*TB)`. Сопоставление по временным меткам даёт ложный результат из-за VFR исходника — см. §4.3.
- Размеры — в единицах Проводника Windows: 1 МБ = 1024² байт.
- «1% low» — значение VMAF на худшем 1% кадров. Оно показывает провалы качества в тяжёлых сценах.

Как читать VMAF: **≥ 95** — практически неотличимо от исходника; **93–95** — отличное качество, разница заметна только при прямом сравнении кадров; **90–93** — хорошее, небольшие потери в мелких деталях; **< 88** — потери заметны при обычном просмотре.

## 3. Решения

### R-1. Единый «индекс качества» и шкала процентов

Ползунок (0–100%) переводится в **индекс качества I**. Шкала индекса совпадает со шкалой CQ у `hevc_nvenc`, потому что это кодировщик по умолчанию:

```
I = 20 + 0.2 × P        (P — проценты 0..100, I — 20..40, дробный)
```

Индекс переводится в параметр конкретного кодировщика так, чтобы **при одном и том же проценте качество (VMAF) было примерно одинаковым**:

| Кодировщик    | Параметр | Формула            | Основание |
|---------------|----------|--------------------|-----------|
| `hevc_nvenc`  | `-cq`    | `I`                | Шкала индекса совпадает с ним по определению |
| `h264_nvenc`  | `-cq`    | `I`                | При одинаковом CQ VMAF совпадает с HEVC в пределах ±0,3 (§2.4); файл больше в ~1,5–1,9 раза |
| `libx265`     | `-crf`   | `0.9 × I − 8.5`    | Подгонка по точкам равного VMAF (§2.5), погрешность ±0,5 CRF |
| `libx264`     | `-crf`   | `0.85 × I − 6`     | Калибровка по 2 точкам (§2.4), **приблизительно** |

Все четыре кодировщика принимают дробные значения, поэтому у шага 1% на ползунке есть реальный эффект.

### R-2. Именованные уровни (US-2)

| Уровень              | %    | I  | Ожидаемо на эталоне (GPU, HEVC) | VMAF  |
|----------------------|------|----|----------------------------------|-------|
| Минимальное          | 25%  | 25 | ~80 МБ (2,4×)                    | ~95,6 |
| **Сбалансированное** | 50%  | 30 | **38,2 МБ (5,0×)**               | 93,97 |
| Сильное              | 75%  | 35 | ~20 МБ (9,5×)                    | ~90,9 |
| Максимальное         | 100% | 40 | 10,7 МБ (17,8×)                  | 86,15 |

Проверка по критериям успеха:
- **SC-001:** 38,2 МБ ≤ 40 МБ. ✅
- **SC-002:** VMAF 93,97, на худших кадрах 93,07 — отличное качество без провалов. Визуальную проверку выполняет пользователь.
- **SC-003:** на уровне «Минимальное» VMAF ~95,6, а файл в 2,4 раза меньше. ✅
- **SC-005:** ~43 с на 65,6 с видео, то есть ~0,65× длительности при ориентире ≤ 2×. ✅

### R-3. Остальные параметры

| Параметр | Решение | Почему |
|----------|---------|--------|
| Пиксельный формат | `-pix_fmt yuv420p` | Совместимость с плеерами и Telegram (FR-002); 10-бит не нужен для SDR-источника |
| Тег HEVC | `-tag:v hvc1` | Без него HEVC в MP4 не открывается в части плееров (QuickTime, iOS) |
| Звук | AAC 160 кбит/с на дорожку, все дорожки: `-map 0:a?` | FR-003. Исходник ~195 кбит/с; 160 кбит/с прозрачно для игрового звука, а прибавка к размеру ~0,26 МБ/мин незаметна |
| Faststart | `-movflags +faststart` | FR-002 |
| Декодирование | Программное, без `-hwaccel` | CUDA-декодер не поднялся на эталоне и откатился на CPU, скорость та же (42,8 с против 42,6 с): узкое место — кодирование. Лишняя точка отказа без выгоды |
| VFR | Режим FFmpeg по умолчанию (без `-fps_mode`) | На эталоне: 3937 кадров на входе и выходе, длительность видео 65,617 → 65,616 с, звука 65,473 → 65,473 с — рассинхрона нет (FR-004) |
| Масштабирование | `scale=-2:<H>:flags=lanczos`, только если высота исходника > H | US-3.2–3.4: не увеличивать, сохранять пропорции, ширина чётная |
| FPS | фильтр `fps=<N>`, только если FPS исходника > N + 0,5 | US-3.3: не повышать; допуск учитывает 59,99 fps у VFR |
| Порядок фильтров | сначала `fps`, затем `scale` | Масштабируются только оставшиеся кадры — меньше работы |
| Пресет x265 | `medium` | `slow` ≈ ещё ×2 по времени ради нескольких процентов — против NFR-002 |
| Пресет x264 | `medium` | Аналогично |

## 4. Отброшенные варианты и находки

1. **`p7` + multipass у NVENC** — +30% времени ради −0,3% размера (§2.2).
2. **Аппаратное декодирование** — выгоды нет (R-3).
3. **Сопоставление кадров VMAF по временным меткам.** NVIDIA App пишет переменную частоту кадров (59,99 fps), а результат выходит ровно 60 fps. При сопоставлении по меткам VMAF сравнивал соседние кадры и выдавал ложные ~71 вместо ~94. Для будущих замеров нужно сопоставлять кадры по номеру.
4. **AV1 (`av1_nvenc`)** — есть в FFmpeg, но аппаратное AV1-кодирование появилось только в RTX 40xx. На RTX 3060 Ti его нет, а программный AV1 слишком медленный для NFR-002. Кандидат на будущее.
5. **Режим целевого размера (2-pass по битрейту)** — вне рамок v1 (spec §3).

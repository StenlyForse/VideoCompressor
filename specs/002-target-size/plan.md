## 1. Технический контекст

Стек без изменений, новых зависимостей нет. Всё, что касается битрейта, проходов, допустимости цели и предложений, — в ядре и покрывается тестами (принцип 2 v1).

## 2. Ядро

### 2.1. Настройки

```csharp
// CompressionSettings — новое необязательное поле:
long? TargetSizeBytes = null;   // null — режим «Степень сжатия» (v1); иначе — «Целевой размер»
```

В режиме цели `CompressionPercent` игнорируется; формат, кодировщик, разрешение, FPS — как в v1 (spec US-1.5).

### 2.2. `Compression/TargetSizePlanner.cs` (чистая логика, research R-1, R-5, R-6)

```csharp
record TargetPlan(int VideoBitrateKbps, double BitsPerPixel, TargetVerdict Verdict, Suggestion? Suggestion, long? MinReasonableSizeBytes);
enum TargetVerdict { Ok, AlreadySmaller, LowQuality, Impossible }
record Suggestion(int? MaxHeight, int? MaxFps);   // что предложить применить

static TargetPlan Plan(VideoInfo source, CompressionSettings settings);
```

- Бюджет и битрейт — research §1 (звук: 160 кбит/с × число дорожек).
- Эффективные размеры кадра и FPS — с учётом лимитов, по тем же правилам, что фильтры в `FfmpegArgumentsBuilder` (не увеличивать, допуск FPS 0,5). Эти правила выносятся в общий помощник, чтобы аргументы и оценка не разошлись.
- `AlreadySmaller` — исходник ≤ цели (spec US-2).
- `Impossible` — звук ≥ бюджета или видео < 50 кбит/с (US-3.4).
- `LowQuality` — bpp ниже порога (0,008 H.265 / 0,012 H.264); `Suggestion` — первый вариант из ряда «30 fps» → «30 fps + 1080p» → «30 fps + 720p», где порог выполняется и который действительно что-то меняет; иначе `MinReasonableSizeBytes` — минимальная цель для исходных параметров, округлённая вверх до 1 МБ.

### 2.3. `FfmpegArgumentsBuilder` — режим цели

- GPU: вместо `-rc vbr -cq {I} -b:v 0` — `-rc vbr -b:v {B}k -maxrate {B}k -bufsize {2B}k -multipass fullres` (research R-2); остальные параметры NVENC те же.
- CPU: новый метод `BuildTwoPass(...)` → два списка аргументов: проход 1 (`-pass 1 -passlogfile <tmp> -an -f null` + `NUL`/`/dev/null` по ОС) и проход 2 (`-pass 2 -passlogfile <tmp>` + обычный выход). `-crf` заменяется на `-b:v {B}k`.

### 2.4. `VideoCompressionService` — исполнение

- Режим цели на CPU: два запуска FFmpeg подряд; прогресс 0–50% / 50–100%; временная папка для журнала проходов (`Path.GetTempPath()/VideoCompressor/<guid>`) удаляется в `finally`.
- **Страховка (R-4):** если результат > цели — одно повторное кодирование с поправленным битрейтом; если снова больше — `FfmpegException("Не удалось уложиться в {N} МБ…")`, файл удаляется. Прогресс повторного прохода показывается как «Уточнение размера…».
- Отмена, очистка недописанного, ошибки — как в v1.

### 2.5. Очередь

`BatchCompressionService` не меняется по сути: режим цели приходит в `CompressionSettings` и применяется к каждому файлу (spec FR-003). Файлы `AlreadySmaller` UI исключает из запуска или включает — по ответу пользователя (§3.3).

## 3. Приложение

### 3.1. Настройки (`MainViewModel`)

- `IsTargetSizeMode` (переключатель «Степень сжатия» / «Целевой размер»).
- `TargetSizes`: «10 МБ — Discord без Nitro», «25 МБ — почта», «50 МБ», «Своё значение»; `CustomTargetMb` (целое, 1–100 000).
- Сохраняются в `settings.json` (`Mode`, `TargetSizeMb`) — spec US-1.6.

### 3.2. Окно

```
Режим            (•) Степень сжатия   ( ) Целевой размер
Целевой размер   [ 25 МБ — почта ▾ ]   [ 25 ] МБ    ← поле только для «Своё значение»
                 ⚠ Для 1440p 60 fps 10 МБ мало — качество будет низким.
                   Лучше: 30 fps (и 1080p).  [ Применить ]
```

- В режиме цели блок «Степень сжатия» (список уровней и ползунок) скрыт, вместо него — выбор размера.
- Предупреждение (US-3) пересчитывается при смене файла, размера, формата, разрешения или FPS; кнопка «Применить» выставляет разрешение / FPS в «Дополнительно».
- Для очереди предупреждение строится по самому «трудному» файлу (наименьший bpp); у файлов, которые уже меньше цели, — пометка в строке «Уже меньше 25 МБ».

### 3.3. Запуск

- Есть файлы `Impossible` → «Сжать» недоступна, объяснение под выбором размера.
- Есть файлы `AlreadySmaller` → перед запуском вопрос «N файл(ов) уже меньше 25 МБ. Сжать их всё равно?» — «Нет» помечает их «Пропущен: уже меньше цели» (spec US-2).
- `LowQuality` не блокирует (US-3.3).

## 4. Тестирование

| Уровень | Что | Как |
|---------|-----|-----|
| Юнит | `TargetSizePlanner`: битрейт и bpp для эталона (25 МБ → 2 940 кбит/с), `AlreadySmaller`, `Impossible`, порядок предложений (30 fps → 1080p → 720p), «не предлагать то, что ничего не меняет», минимальный размер | Без FFmpeg |
| Юнит | Аргументы: GPU в режиме цели (`-maxrate = -b:v`, без `-cq`), два прохода CPU (`-pass 1`/`-pass 2`, `-an`, null-выход по ОС) | Без FFmpeg |
| Интеграция | CPU x264 и x265, 20-секундный клип, цель → результат ≤ цели и ≥ 85%; временные файлы проходов удалены; отмена во время 1-го и 2-го прохода | Сгенерированный клип |
| Интеграция | GPU — то же, если NVENC доступен | Пропуск без NVENC |
| Через UI | SC-001…SC-004 на эталоне | Скрипты UIA, как в v1 |

## 5. Известные ограничения

- CPU H.265 до цели ~2,3× времени обычного сжатия (research R-7) — чуть выше ориентира SC-004; GPU — 1,15×.
- Пороги bpp откалиброваны на одной игровой записи (как и уровни v1).
